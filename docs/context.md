# Contexto do Projeto — Carlesso Pilates Frontend

## O que é este projeto

O **Carlesso Pilates Frontend** é uma aplicação web Angular desenvolvida para apoiar a gestão administrativa de um estúdio de pilates. O sistema centraliza o cadastro e controle de pacientes, servindo como ponto de partida para um sistema mais amplo de gestão do estúdio.

A aplicação consome uma API REST que roda localmente em `http://localhost:8080`, construída separadamente (backend Spring Boot, presumidamente). Durante o desenvolvimento, todas as chamadas passam por um proxy do Angular CLI (`/api/*` → `localhost:8080/*`) para contornar restrições de CORS.

Performance (issue #25): adoção de `ChangeDetectionStrategy.OnPush` nos componentes de listagem `PacienteListComponent`, `ProfissionalListComponent`, `PlanoListComponent`, `PagamentoListComponent` e `AulaListComponent`, alinhando-os ao padrão já usado no `DashboardComponent`. Com a estratégia padrão (`Default`) o Angular roda change detection em todos os componentes a cada evento do browser; com `OnPush` o componente só é verificado quando uma referência de `@Input` muda, quando emite um evento ou quando é marcado explicitamente. Cada componente passou a injetar `ChangeDetectorRef` e a chamar `cdr.markForCheck()` ao final de cada atualização assíncrona de estado (callbacks `next`/`error` das assinaturas de `carregar`, `inativar`, `ativar`, `confirmarPagar`, `realizar`, `carregarProfissionais` e resolução do pagamento na rota de aulas), garantindo que a UI continue refletindo o estado após chamadas à API. Como complemento direto do `OnPush`, as tabelas de cada listagem ganharam `trackBy` (`trackByPaciente`, `trackByProfissional`, `trackByPlano`, `trackByPagamento`, `trackByAula`, todas por `id`), evitando que o Angular destrua e recrie todas as `<tr>` a cada recarga — já que `carregar()` reatribui o array de itens com uma nova referência. As assinaturas HTTP passaram a usar `takeUntilDestroyed(this.destroyRef)`, espelhando integralmente o padrão do `DashboardComponent`. Cobertura adicional valida que cada listagem usa `OnPush` (via o helper de teste `isOnPush`, em `src/testing/onpush.ts`, que isola num único ponto o acesso à API interna `ɵcmp`) e que `markForCheck` é disparado após o carregamento da lista.

51. Implementação do diálogo de confirmação compartilhado (issue #140). O `ConfirmarDialogComponent` (`shared/components/confirmar-dialog`), até então um stub gerado, passou a concentrar todos os diálogos de confirmação da aplicação: expõe os inputs `titulo`, `mensagem`, `textoConfirmar`, `textoCancelar`, `variante` (`primaria`/`secundaria`/`perigo`, mapeadas para `btn-primary`/`btn-secondary`/`btn-danger`), `processando`, `confirmarDesabilitado` e `fecharAoClicarFora`, os outputs `confirmar` e `cancelar`, e um `<ng-content>` para conteúdo projetado quando a mensagem não é um texto simples (ex.: nome em negrito nas telas de detalhe e o formulário de data no diálogo de pagamento). A acessibilidade ficou centralizada no componente: `role="dialog"`, `aria-modal="true"`, `aria-labelledby` apontando para o título gerado com id único, foco inicial no botão de confirmação (ou no primeiro elemento focável quando ele começa desabilitado, como no diálogo de pagamento), focus trap em Tab/Shift+Tab, fechamento por Esc e devolução do foco ao elemento disparador no `ngOnDestroy`. Enquanto `processando` está ativo, os botões de confirmar e cancelar ficam desabilitados e Esc não fecha o diálogo, evitando duplo disparo da ação — e **todas** as telas que confirmam ações mantêm um estado de ação em andamento (`acaoEmAndamento`/`acaoEmAndamentoId`) que é bindado nesse input e também protege o método de execução com early return, de modo que um duplo clique não dispara duas requisições. O `aria-describedby` aponta para o corpo do diálogo (mensagem ou conteúdo projetado) e, enquanto aberto, o componente aplica a classe `dialog-aberto` no `body` para travar o scroll do conteúdo de fundo. O fechamento por clique no overlay é o padrão (`fecharAoClicarFora` = `true`), desligado apenas no diálogo de pagamento, onde há formulário preenchido e o clique acidental fora causaria perda de dados. 57. Tratamento global de `403` no interceptor HTTP (issue #116). Até então apenas o `401` tinha tratamento global; um `403` da API (usuário autenticado, sem permissão para o recurso) chegava ao componente, que podia ou não exibir mensagem — a rota `/403` só era alcançada pelo `roleGuard`, na navegação. Foi criado o `forbiddenInterceptor` (`core/interceptors/forbidden.interceptor.ts`), registrado após o `authInterceptor` em `app.config.ts`, mantendo o fluxo de `401` intacto e sem tocar em `accessToken`/`currentUser` no `localStorage`. O tratamento global só vale para sessões ativas (`authService.isAuthenticated()`, mesma condição do `authInterceptor`): nos endpoints públicos (`/auth/login`, `/auth/forgot-password`, `/auth/reset-password`) um `403` significa "sem login", não "sem permissão", e é propagado para a própria tela exibir sua mensagem, sem banner global nem redirecionamento. A distinção entre "carregamento de tela" e "ação pontual" é feita pelo método HTTP: `403` em `GET` (a forma como as telas carregam seus dados) navega para `/403`; `403` em `POST`/`PUT`/`PATCH`/`DELETE` (ação disparada pelo usuário) exibe a mensagem padrão "Acesso negado: você não tem permissão para realizar esta ação." e mantém o usuário na tela. A mensagem é publicada pelo novo `NotificacaoService` (`core/services/notificacao.service.ts`, signal `notificacao` com `erro()`/`limpar()`) e renderizada pelo `AppComponent` como banner `.alert.alert-danger` com `role="alert"` acima do `router-outlet`, dismissível e limpo automaticamente a cada `NavigationEnd`. Para telas que já tratam `403` localmente e passariam a exibir mensagem duplicada ou navegar sem necessidade, o interceptor respeita o `HttpContextToken` `TRATA_403_LOCALMENTE`: as chamadas do `NfseEmitidaService` (listar/salvar NFSE, cujas telas usam `extrairMensagemErro`) e o `UsuarioAdminService.alterarSenha` marcam o contexto com `true` e ficam fora do tratamento global. Cobertura: `forbidden.interceptor.spec.ts` (redirecionamento em `GET`, mensagem sem navegação em ação pontual, sessão preservada, opt-out via `HttpContext`, indiferença a status não-`403`) e `notificacao.service.spec.ts`.

59. Busca global na navbar (issue #121). Localizar um paciente exigia navegar até `/pacientes` e preencher os filtros da listagem. O `BuscaGlobalComponent` (`shared/components/busca-global`, standalone e `OnPush`) foi adicionado às `.navbar-actions` do `AppComponent` e reusa os endpoints já paginados: `GET /api/pacientes` (via `PacienteService.listar`) e, apenas para `ADMIN`, `GET /api/profissionais` (via `ProfissionalService.listar`), ambos com `size` reduzido a 5. O campo usa um `FormControl` com `debounceTime(300)` + `distinctUntilChanged` e só dispara a busca a partir de 2 caracteres, evitando uma requisição por tecla e consultas que trariam a base inteira. O termo é classificado pelo formato: valores compostos apenas por dígitos e pontuação de máscara (`.`, `-`, espaço) viram filtro `cpf`; os demais viram filtro `nome`. O termo vai para a API **como digitado**, sem normalização: os filtros `nome`/`cpf` do backend são `LIKE %termo%` (`contemIgnorandoCase` em `PacienteService`/`ProfissionalService`) sobre o valor gravado, e o cadastro persiste o CPF exatamente como preenchido (não há máscara nem normalização no `PacienteRequestDTO`) — reduzir o termo a dígitos faria `12345678901` deixar de casar com um `123.456.789-01` salvo. Como o `LIKE` é parcial, buscar por parte do CPF funciona e o mínimo de 2 caracteres vale também para o termo numérico. Nenhum filtro envia `ativo`, e o `porStatus` do backend trata `ativo == null` como `true`: a busca devolve apenas registros ativos, mesmo padrão das listagens. A requisição de profissionais **não é disparada** para perfis não-`ADMIN` — o backend responderia `403` e o `forbiddenInterceptor` redirecionaria a tela para `/403` — nem quando o termo é um CPF, já que o endpoint não filtra por esse campo. As duas buscas são combinadas com `combineLatest` e cada ramo devolve `{ resultados, falhou }` no `catchError`, em vez de uma lista vazia: assim a falha de um tipo não apaga os resultados do outro **e** uma falha de rede não é confundida com "não existe" — sem nenhum resultado, o dropdown exibe "Não foi possível buscar agora. Tente novamente." em vez de "Nenhum resultado encontrado.". O dropdown segue o padrão ARIA de combobox com `aria-activedescendant`: setas ↑/↓ percorrem a lista (com wrap), Enter abre `/pacientes/:id` ou `/profissionais/:id`, Esc fecha e o clique fora fecha via `HostListener`. O Esc chama `stopPropagation()` porque o `AppComponent` fecha a navbar colapsada em `document:keydown.escape` — sem isso, dispensar o dropdown no mobile fecharia o menu inteiro. As mensagens de estado ficam numa live region `aria-live="polite"` **sempre presente no DOM** (escondida por clip quando vazia, já que leitores de tela só anunciam a mudança de uma região que já existia). O foco no campo é acessível por atalho global: `Ctrl`/`Cmd`+`K` de qualquer lugar e `/` quando o foco não está em outro campo de texto — o `focus()` é adiado com `setTimeout`, porque focar ainda dentro do `keydown` fazia o próprio caractere `/` ser inserido no campo (validado no navegador: o campo abria com `/` já digitado, quebrando a busca seguinte). Ao selecionar um resultado o controle é limpo **emitindo** no stream, para que o `distinctUntilChanged` não engula uma nova digitação do mesmo termo logo em seguida. Mudança exclusivamente de frontend, sem endpoint novo. Cobertura em `busca-global.component.spec.ts`: debounce e termo mínimo, filtro por nome vs. CPF (máscara preservada e busca parcial), ausência de chamada a profissionais para não-`ADMIN` e para termos de CPF, mescla de resultados para `ADMIN`, resiliência à falha de um dos ramos, estado de erro distinto do de lista vazia, live region persistente, navegação por teclado e clique do mouse até o detalhe, Esc com `stopPropagation`, fechamento por clique fora e os dois atalhos de foco; em `app.component.spec.ts`, a presença do `<app-busca-global>` nas `.navbar-actions` apenas com sessão ativa.

68. Resultados da análise postural — Tela 3 do "Simetrógrafo Virtual" (issue #183): medidas calculadas, destaque de assimetrias, observações clínicas e conclusão. Cobertura: `metricas-posturais.spec.ts` (ângulos com e sem proporção, normalização do ângulo, desvio de prumo frontal/lateral, direção sob vista espelhada, limiar em 1,9° vs 2,0°, cm só com calibração), `painel-medidas-posturais.component.spec.ts` (pendências, destaque, recálculo ao mudar os pontos via `setInput` — atribuição direta não marcaria o componente OnPush) e novos casos em `paciente-avaliacao-postural-editor.component.spec.ts` (prévia x API, habilitação do concluir, fluxo `PUT`+`PATCH`, `422`, observações apagadas). Mudança exclusivamente de frontend (novo componente + template/imports das telas), sem alteração de rotas, serviços ou API. Cobertura: `breadcrumb.component.spec.ts` valida a estratégia `OnPush`, a ausência de `<nav>` sem itens, o landmark `nav[aria-label="breadcrumb"]`, a renderização de um item por nível, os links navegáveis em todos os níveis exceto o atual (`href` resolvido pelo `routerLink`), o `aria-current="page"` apenas no último item (renderizado como `<span>`, não como link), o item intermediário sem `link` como texto puro e o separador entre itens (sem separador após o último).

70. Ordenação clicável nas colunas das listagens paginadas (issue #151). As listagens `/pacientes`, `/profissionais` e `/admin/usuarios` eram sempre ordenadas por nome (`sort` fixo no service), impedindo, por exemplo, achar os profissionais com maior % por aula sem paginar manualmente. Agora os cabeçalhos de coluna são clicáveis e alternam a ordenação, enviando o campo escolhido no parâmetro `sort` **já existente** das chamadas (ex.: `sort=email,asc`), sem qualquer mudança de contrato com a API — apenas o valor de `sort` muda, mantendo o mesmo endpoint e o Pageable do Spring. Novo model `core/models/ordenacao.ts` concentra o estado de ordenação (`Ordenacao = { campo, direcao }`, `DirecaoOrdenacao = 'asc' | 'desc'`), a conversão para o parâmetro `sort` (`toSortParam` → `'campo,direcao'`) e o ciclo de clique (`proximaOrdenacao`): coluna diferente → asc; mesma coluna asc → desc; mesma coluna desc → **volta ao padrão** (nome asc; `name` na tela de usuários, cujo backend usa esse campo), sem mutar os argumentos. Novo componente compartilhado `SortableHeaderComponent` (`shared/components/sortable-header/`, standalone e `OnPush`, mesmo padrão de `pagination-summary`/`confirmar-dialog`): aplicado como atributo no `<th>` (`th[app-sortable]`, preservando a semântica da tabela e o `aria-sort` no próprio cabeçalho), projeta o rótulo original da coluna via `<ng-content>` e adiciona um `<button>` acessível que emite o campo clicado; expõe `[attr.aria-sort]` (`ascending`/`descending`/`none`) refletindo a coluna/direção ativa e exibe seta `▲`/`▼` na coluna ativa e um indicador neutro `⇅` (revelado no hover/foco) nas demais. Para habilitar componentes de seletor por atributo, a regra `@angular-eslint/component-selector` do `eslint.config.js` passou a aceitar `type: ["element", "attribute"]` (antes só `element`). Cada listagem ganhou o estado `ordenacao`/`ordenacaoPadrao` e o método `ordenar(campo)`, que calcula a próxima ordenação (nova referência, para os cabeçalhos `OnPush` refletirem a mudança), **reseta para a página 0** e recarrega — como `carregar()` reaplica `montarFiltro()`, os filtros ativos são preservados. Já as ações **Buscar** e **Limpar** dos filtros (pacientes/profissionais) voltam a ordenação para o padrão (`nome asc`), para que uma nova busca parta sempre da ordem conhecida. Os services `PacienteService.listar` e `ProfissionalService.listar` receberam um 4º parâmetro opcional `sort` (default `'nome'`, mantendo o comportamento anterior); `UsuarioAdminService.listar` já expunha `sort` (default `'name'`). Colunas ordenáveis por tela, restritas aos campos simples do DTO exibidos em coluna: pacientes → nome, e-mail e status (`ativo`); profissionais → nome, e-mail, contrato (`tipoContrato`) e % por aula (`percentualPagamentoAula`); usuários → nome (`name`), e-mail, perfil (`role`) e status (`active`). Mudança exclusivamente de frontend, sem endpoint novo. Cobertura: `ordenacao.spec.ts` (formatação do `sort` e ciclo asc→desc→padrão, sem mutação), `sortable-header.component.spec.ts` (projeção do rótulo, `aria-sort` da coluna ativa/inativa, emissão do campo no clique, seta ativa vs. indicador neutro), novos casos nos três specs de listagem (ordem inicial, reset de página, preservação de filtros, ciclo asc→desc→padrão e `aria-sort` no DOM) e novos testes de service validando o envio do `sort` customizado (`paciente`/`profissional`).

71. Correção dos campos não persistidos no formulário de edição de sessão (issue #173). Em `/pacientes/:pacienteId/sessoes/:id/editar` os campos **Status**, **Tipo** e **Profissional** apareciam editáveis, mas nenhum deles era aplicado pelo `PUT /api/sessoes/{id}`: o backend só expõe `data`, `horario`, `local`, `duracaoMinutos` e `observacoes` no `SessaoPilatesUpdateDTO`, de modo que o `status` enviado pelo `toApiUpdate` era descartado pelo Jackson e `tipo`/`profissionalId` sequer chegavam a ser enviados. O usuário alterava qualquer um dos três, via a mensagem "Sessão atualizada com sucesso." e, ao recarregar, encontrava o valor anterior — falha silenciosa, sem erro de API nem aviso na tela. A correção alinha a interface ao contrato que a API sempre teve, sem tocar em nenhum endpoint: os três campos passam a ser **somente informativos na edição** (`disable()` no `ngOnInit` quando `modoEdicao`, mesmo padrão já usado pelo CPF imutável do `paciente-form`), cada um com um `field-hint` explicando o motivo — tipo e profissional são "definidos no agendamento", o status é "alterado pelas ações Realizar e Cancelar na listagem de sessões". No modo de criação nada muda: `tipo` e `profissionalId` continuam editáveis e o `POST /api/sessoes` continua aceitando ambos. O `SessaoUpdateDTO` (`core/models/sessao.ts`) foi reduzido a `dataHora`, `duracao` e `observacoes`, e `SessaoService.toApiUpdate` deixou de enviar `status` no corpo. Como `salvar()` passou a usar `form.getRawValue()`, os controles desabilitados não vazam para o payload nem quebram a montagem do `SessaoRequestDTO` da criação. A alteração de status de uma sessão existente continua exclusivamente pelos `PATCH /api/sessoes/{id}/realizar` e `PATCH /api/sessoes/{id}/cancelar` da listagem, que validam a transição (só aceitam sessão `AGENDADA`) — permitir status pelo `PUT` abriria um bypass dessas regras. Permitir a troca de tipo ou profissional de uma sessão já criada ficou fora de escopo: nunca existiu e exigiria mudança de backend. Cobertura: `sessao.service.spec.ts` assertando o corpo exato do `PUT` (apenas `data`, `horario`, `duracaoMinutos` e `observacoes`) e `paciente-sessao-form.component.spec.ts` cobrindo quais controles ficam habilitados em criação vs. edição, o `disabled` no DOM e o payload do `atualizar` mesmo quando os campos informativos são alterados via `patchValue`.

72. Padrão único de validação de formulários: submit habilitado, `markAllAsTouched` e foco no primeiro campo inválido (issue #148). Dois padrões conviviam nos formulários: o login (e as telas públicas de senha) **desabilitava o botão** enquanto o form era inválido — o usuário clicava e nada acontecia, sem saber o motivo —, enquanto os demais já permitiam o submit e chamavam `markAllAsTouched()` para revelar os erros; em nenhum deles o foco ia para o primeiro campo com erro, então em formulários longos do prontuário a mensagem podia ficar fora da viewport. A correção adota um único padrão em todos os formulários: submit sempre habilitado (o `[disabled]` fica só com o estado de salvamento — `carregando`/`enviando`/`salvando`/`processando`), `markAllAsTouched()` no submit inválido e **foco + scroll até o primeiro campo com erro**, mais foco inicial no primeiro campo ao abrir telas de criação. Novo helper compartilhado `shared/utils/form-focus.ts` com duas funções puras sobre o DOM: `focarPrimeiroInvalido(form, host)` — retorna `false` cedo quando `form.valid`, senão faz `querySelector('input.ng-invalid:not([disabled]), select…, textarea…')` no host e foca+`scrollIntoView({ block: 'center' })` o primeiro em ordem de documento (a ordem do DOM já reflete a ordem visual dos campos; a classe `ng-invalid` do Angular existe independentemente de `touched`, então funciona logo após o `markAllAsTouched`) — e `focarPrimeiroCampo(host)` — foca o primeiro campo focável ignorando `type=hidden` e desabilitados. Ambas aceitam `ElementRef` ou `HTMLElement`. Cada componente de formulário injeta o `ElementRef` do host e chama `focarPrimeiroInvalido(this.form, this.host)` no ramo inválido do submit. O `[disabled]="form.invalid || …"` foi removido do login, `forgot-password`, `reset-password` e `alterar-senha`, e o login (que só dava `return` no inválido) passou a marcar touched + focar. Os dois diálogos modais que desabilitavam o confirmar por invalidez (`[confirmarDesabilitado]="…invalid"`) — reagendamento em `paciente-sessao-list` e confirmação de pagamento em `pagamento-list` — deixaram de desabilitar e passaram a marcar touched + focar no `confirmar`. O foco inicial na criação usa `ngAfterViewInit` → `focarPrimeiroCampo` nas telas de entrada síncronas (login, forgot/reset senha, alterar senha, `paciente-form`/`profissional-form`/`usuario-form` em modo criação, `plano-form`, `pagamento-form` e os dois relatórios); nas telas do prontuário que decidem criação × edição só depois de carregar o registro (anamnese, avaliação fisioterapêutica, sessão, evolução, reavaliação, plano de tratamento, NFSE), o foco é chamado no ramo "sem registro" do callback de carga e **adiado com `setTimeout`**, porque o formulário só entra no DOM depois que o `*ngIf="!loading"` renderiza. O `paciente-avaliacao-postural-form` (seleção de vista por cards + upload de foto, submit já governado por `enviando`/`comprimindo`) recebeu apenas o foco no inválido. Mudança exclusivamente de frontend, sem endpoint novo. Cobertura: `form-focus.spec.ts` (foco no primeiro inválido em ordem de documento, suporte a select/textarea, ignora desabilitados, aceita `ElementRef`, no-op quando o form é válido/sem host; foco do primeiro campo pulando ocultos/desabilitados) e novos casos de componente (`login.component.spec.ts` e `paciente-form.component.spec.ts`: submit permanece habilitado com form inválido, foco no primeiro inválido e foco inicial na criação; `paciente-anamnese.component.spec.ts`: foco inicial adiado na criação e foco no inválido). Os specs que instanciam o componente manualmente (`plano-form`, `pagamento-form`, `pagamento-list`) passaram a receber um `ElementRef` no construtor.

73. Correção do enquadramento do botão **Voltar à Administração** na listagem de usuários (issue #199). Em `/admin/usuarios`, o rótulo do botão aparecia colado no topo da borda, com um vão vazio ocupando a metade inferior — defeito visível em qualquer viewport e evidente no mobile, onde o botão fica sozinho no rodapé da página. A causa era o `display: inline-block` declarado em `.back-link` (`usuario-list.component.scss`): como o SCSS de componente ganha o atributo `[_ngcontent-*]` do encapsulamento emulado, ele vence em especificidade o `.btn` global (`styles.scss`), que monta o botão como `inline-flex` e centraliza o rótulo por `align-items`/`justify-content`. Trocado o `display`, essas duas propriedades ficam inertes e, como o `.btn` não tem padding vertical (`padding: 0 var(--sp-5)`) e usa `line-height: 1`, o texto se apoiava no topo enquanto o `min-height: var(--btn-h)` mantinha a altura total. A correção remove o override de `display` — restando ao componente apenas o espaçamento externo, agora com o token `--sp-6` (24px, o mesmo valor do `1.5rem` anterior) — e o botão volta a ser idêntico aos demais `.btn btn-outline` do sistema. Medição antes × depois no CSS compilado, nas seis combinações de tema (claro/escuro) × densidade (`default` 40px, `compact` 34px, `comfortable` 44px): a folga acima do rótulo saiu de 0px com 19–29px sobrando embaixo, para folga simétrica e desvio do centro igual a 0 em todos os casos, sem alterar a altura do botão. Auditoria confirmou que `.back-link` era o **único** override de `display` sobre um `.btn` no projeto: `.status` no mesmo arquivo é um `<span>` (legítimo), `.palco` do simetrógrafo é um `<div>`, `.btn-entrar`/`.btn-enviar`/`.btn-voltar-login` são classes próprias fora do seletor global, e os overrides de `.btn`/`.btn-sm` em `forbidden` e `aula-list` mexem só em `width`. Mover o botão para dentro do `.page-header`, como fazem as demais telas, ficou fora de escopo por ser decisão de padronização de navegação, não o defeito reportado. Cobertura: novo caso em `usuario-list.component.spec.ts` assertando `getComputedStyle` do `a.back-link` com `display: inline-flex` e `margin-top: 24px` — o guard foi verificado contra o CSS antigo e falha com `Expected 'inline-block' to be 'inline-flex'`. Convenção registrada no README: em SCSS de página, sobrescrever de um componente global apenas o que o posiciona no layout (`margin` e, quando necessário, `width` — como já fazem `forbidden` e `aula-list` para botões de largura total no mobile), nunca as propriedades que montam o interior do componente (`display`, `padding`, `min-height`, `line-height`).

74. Correção da seta dos selects, que renderizava em tamanho gigante, e padronização dela em toda a aplicação (issue #200). No campo **Perfil** de `/admin/usuarios/:id/editar` — e em todos os demais `select.form-control` — a seta ocupava a altura inteira do campo em vez dos 12×8px pretendidos. A causa era o SVG do data URI declarar apenas `viewBox='0 0 12 8'`, sem `width`/`height`, combinado com a ausência de `background-size` na regra global (`styles.scss`): um SVG assim tem proporção intrínseca (3:2) mas **nenhum tamanho intrínseco**, e o algoritmo padrão do CSS (Images 3, §5.5) com `background-size: auto` ajusta a imagem por *contain* contra a área de posicionamento do fundo, escalando-a até a altura do campo — 60×40px na densidade padrão, 66×44 na `comfortable` e 51×34 na `compact`, sempre invadindo o texto, já que o `padding-right: 36px` foi calculado para uma seta de 12px. A correção declara `background-size: 12px 8px` e acrescenta `width='12' height='8'` ao SVG, defesa dupla para o defeito não voltar caso a regra seja reescrita. O desenho saiu da regra e virou o token `--select-chevron` (`src/styles/_tokens.scss`), com uma versão por tema: o stroke mora dentro do data URI e `url()` não interpola `var()`, então `[data-theme="dark"]` substitui o token inteiro pelo mesmo desenho em `#b9bcc1` (o `--text-secondary` escuro). O grafite `#455157` do tema claro rendia ~2:1 sobre o `--bg-elev` escuro, abaixo do mínimo de 3:1 da WCAG 1.4.11 para componentes de interface; medidos agora 8,2:1 no claro e 8,4:1 no escuro. Além do tamanho, a auditoria mostrou que **metade dos selects nem chegava a receber a seta customizada**: os 5 campos sem `class="form-control"` (filtros de `paciente-list` e `profissional-list`, seletor de itens por página do `pagination-summary` compartilhado e da cópia local em `paciente-list`) exibiam a seta nativa do sistema operacional, e o `select.form-control-sm` de `aula-list` não exibia seta **alguma** — o `appearance: none` global removia a nativa e a shorthand `background: var(--bg-elev)` do SCSS do componente, que vence o global em especificidade por causa do atributo `[_ngcontent-*]`, zerava o `background-image`. Todos os 5 selects passaram a usar `.form-control` e, como o SCSS local desses componentes redeclarava o campo inteiro (altura fixa de 38px, `padding` que roubava o espaço da seta, a shorthand `background`, borda e foco duplicados do global), essa cópia foi removida — os `input` dos mesmos filtros também passaram a `.form-control` para a linha não ficar com campos de alturas diferentes. Efeito colateral desejado: os filtros deixam de ter altura fixa e passam a acompanhar a densidade (34/40/44px), como o resto dos formulários, e herdam do global o salto para `font-size: 16px` no mobile que evita o zoom do Safari iOS (issue #160), antes duplicado em cada componente. Nos casos em que o campo não pode esticar — o seletor de itens por página dentro de um `label` flex —, o componente mantém apenas `width: auto`, que é override de layout e não de interior, conforme a convenção do issue #199. A mesma armadilha apareceu **dentro do próprio estilo global**: a regra `&:disabled` do campo (`.form-control:disabled`, especificidade maior que `select.form-control`) usava `background: var(--bg-sunken)` e apagava a seta de todos os selects desabilitados — defeito pré-existente, encontrado na validação visual e coberto pelo critério de aceite do issue; corrigido para `background-color`. Nova regra global `select.form-control-sm` aproxima a seta da borda (`right 8px`) e reduz o `padding-right` para 26px, já que o campo pequeno tem 32px de altura e recuo horizontal de 12px e herdaria os 36px pensados para o campo padrão. A tríade utilitária `.input`/`.select`/`.textarea` foi **removida** do `styles.scss`: nenhum template a usava, e mantê-la significaria replicar em cada regra nova (seta, `background-size`, recuo) um caminho de estilo que ninguém exercita. O protótipo do Design System conserva as classes no seu próprio `assets/tokens.css`, que não entra no build do Angular. A remoção deixa `.form-control` como a única API de campo do app. O mesmo defeito foi corrigido na origem, em `assets/tokens.css`, para que o protótipo do Design System não devolva a regra quebrada ao app na próxima cópia. Ficaram fora de escopo, como previsto no issue: trocar o `<select>` nativo por um combobox customizado e redesenhar o design system de formulários. Cobertura: 7 novos casos assertando `getComputedStyle` com os estilos globais carregados (o `karma` já inclui `src/styles.scss`) — tamanho 12×8 e `padding-right` de 36px no select do `usuario-form`, seta preservada com o controle desabilitado, troca do token no tema escuro, seta preservada com `padding-right` de 26px no `form-control-sm` de `aula-list`, e `.form-control` + seta customizada nos selects de `paciente-list`, `profissional-list` e `pagination-summary`, este último também verificando que o campo não estica dentro do label. Todos os guards foram verificados contra o CSS antigo e falham com `Expected 'auto' to be '12px 8px'`, `Expected 'none' not to be 'none'`, `Expected '8px' to be '26px'` e `Expected '…455157…' to contain 'b9bcc1'`. Três achados do review do PR foram corrigidos no mesmo ciclo. (a) O `font-size: 0.9rem` local do `.form-control-sm` de `aula-list` saiu: vencia por especificidade a regra global que sobe os campos para 16px no mobile e reabria o zoom automático do Safari iOS que a issue #160 havia fechado — o campo passa a usar `--fs-caption` no desktop e 16px no mobile, como os demais. (b) `paciente-list` deixou de duplicar o markup do `.pagination-summary` e passou a consumir o `<app-pagination-summary>` compartilhado — a duplicação era o motivo de a mesma correção precisar ser feita em dois lugares; com ela saíram também `pageStart()`/`pageEnd()` do componente (o cálculo já vivia no compartilhado, com testes próprios), o `alterarTamanhoPagina` passou a receber `number` em vez de `string`, e o SCSS local do resumo — inclusive a media query de 640px, que nunca casou com o DOM do componente filho por causa do atributo de encapsulamento — foi apagado. (c) A tríade utilitária citada acima. O quarto achado, a migração dos inputs dos filtros para `.form-control`, foi mantido: é decisão de padronização, não defeito. Armadilha registrada no README: em elemento que depende de `background-image` herdado do global, usar `background-color:` e nunca a shorthand `background:`.

75. Indicação de scroll horizontal nas tabelas de resultado dos relatórios no mobile (issue #164). Em `/relatorios/pagamento-profissional` (tabelas de 6 e 8 colunas) e `/relatorios/nfse` (8 colunas), as tabelas já rolavam contidas no `.table-responsive`, mas em 375px apenas ~2 colunas cabiam no viewport e nada sinalizava que havia mais à direita: o usuário podia não perceber que **Valor Profissional** — a coluna que interessa — estava fora da tela, e a coluna de identificação da linha (**Data**/**Nome**) rolava junto, dificultando cruzar linha × valor. A correção é só de CSS/markup, sem mudança de contrato. (a) Os contêineres globais `.table-responsive`/`.table-wrap` ganharam sombras de borda em quatro camadas de `background-image`: duas "tampas" opacas da cor do contêiner com `background-attachment: local` — que rolam junto com a tabela — sobre duas sombras presas ao contêiner (`scroll`). Sem transbordo as tampas nunca saem de cima das sombras e nada aparece; ao rolar, a tampa correspondente sai de vista e a sombra da borda oposta surge, tudo sem JavaScript. Como as sombras são pintadas no fundo do contêiner, a tabela dentro dele passou a ter `background-color: transparent` (com fundo próprio ela cobriria as camadas); o visual das linhas não muda, porque o contêiner já é opaco na mesma cor. A cor da sombra vive no token `--table-scroll-shadow`, com versão por tema (`rgba(20, 31, 45, 0.16)` no claro, `rgba(0, 0, 0, 0.55)` no escuro, onde a versão clara quase não se distingue do fundo), espelhado em `src/styles/_tokens.scss` e `assets/tokens.css`. (b) Nova classe utilitária global `.table-sticky-first-col`, aplicada às três tabelas de relatório, congela a primeira coluna com `position: sticky; left: 0` e fundo opaco por token (`--bg-elev` nas células, `--bg-sunken` no cabeçalho) — sem fundo opaco as colunas seguintes passariam por baixo e o texto se sobreporia. O separador da coluna congelada é um pseudo-elemento absoluto de 1px com sombra difusa, e não `border-right` nem `box-shadow` da célula: numa tabela com `border-collapse: collapse` a borda pertence à tabela e o WebKit não a repinta na posição sticky, enquanto o Chromium não pinta box-shadow de célula colapsada — verificado em navegador, o separador simplesmente sumia. Essa sombra também compensa a sombra esquerda do contêiner, que fica encoberta pela coluna congelada. (c) Um `.table-scroll-hint` ("Arraste a tabela para o lado para ver todas as colunas →", com a seta em `aria-hidden`) precede cada tabela e só aparece em ≤768px, junto com o restante das regras mobile do `styles.scss`. A opção de ocultar colunas intermediárias em ≤480px, listada como opcional na issue, não foi implementada: com a coluna congelada e a affordance de scroll, todas as colunas continuam alcançáveis, e o detalhamento completo já está nas exportações PDF/XLSX. Como o fundo do contêiner é o que pinta as sombras, duas listagens que declaravam fundo próprio na tabela em SCSS de componente — `/pacientes` e `/aulas` — passaram a `background-color: transparent` (o SCSS local empata em especificidade com a regra global por causa do atributo de encapsulamento e vencia por ordem de injeção, cobrindo as sombras); no modo card do `/aulas` (≤640px) o fundo elevado foi movido para dentro do media query, onde cada linha é de fato um card. O anel de foco não reaproveita o `--shadow-focus`: com 18% de alfa ele compõe 1,32:1 sobre `--bg-app`, longe dos 3:1 da WCAG 2.4.11, então o contêiner usa `outline: 2px solid var(--text-brand)` (7,2:1 no claro, 9,67:1 no escuro — o `--border-brand` não é redefinido no tema escuro e cairia para 2,26:1); e o media query local dos relatórios passou de 760px para os 768px do bloco mobile global, ficando só com `.form-actions` (o `.form-row` já empilha pela regra global). Os specs dos dois relatórios ganharam guardas de computed style para sticky/fundo opaco (claro e escuro), para as camadas de fundo do contêiner (`background-attachment: local, local, scroll, scroll`) e a transparência da tabela, para a visibilidade do hint por media query, além de regressões dos critérios já atendidos: `summary-grid` em 1 coluna a 375px e botões de ação empilhados no mobile. Esses testes de breakpoint rodam dentro de um iframe de largura fixa (helper `src/testing/viewport.ts`, que serializa as folhas de estilo do documento para dentro dele): a janela do Karma é sempre larga e, com asserções condicionais por `matchMedia`, só o ramo desktop era exercitado — as regras mobile, que são o objeto da issue, ficavam sem teste efetivo.

76. Tela de histórico de evoluções do paciente em linha do tempo, fase 1/3 (issue #205). Até aqui a única forma de ler a evolução clínica era abrir `/pacientes/:pacienteId/sessoes/:sessaoId/evolucao` uma sessão por vez pelo botão **Evolução** da listagem: acompanhar semanas de tratamento significava entrar, ler, voltar e repetir, sem nenhuma visão consolidada. A nova rota `/pacientes/:pacienteId/evolucoes` (`PacienteEvolucaoListComponent`, `authGuard` + `loadComponent`, posicionada entre a listagem de sessões e o bloco de plano de tratamento) entrega essa segunda forma de leitura em uma única página, da evolução mais recente para a mais antiga. A tela é **somente leitura** — nenhum `POST`/`PUT` sai dela —, e a tela de cadastro/edição por sessão continua exatamente como estava, o que mantém o risco de regressão restrito à navegação. O `EvolucaoSessaoService` ganhou `listarPorPaciente` (`GET /api/evolucoes-sessao/paciente/{pacienteId}`), espelhando `ReavaliacaoService.listarPorPaciente`; o endpoint já existia no backend e devolve lista vazia, não `404`, quando o paciente não tem registros. Sessões `AGENDADA`/`CANCELADA` sem evolução ficam de fora. A ordenação é decrescente por data/hora da sessão, com desempate por `sessaoId`, e a coleção derivada (`itens`) mora num único ponto do componente, para que o gráfico de dor (#206) e os filtros de período/tipo (#207) consumam a mesma lista. O componente usa `ChangeDetectionStrategy.OnPush` com `cdr.markForCheck()` após cada atualização assíncrona **e** após alternar a expansão (sem isso o toggle só funcionaria pelo clique no template, que já marca a view suja — o guard de teclado do spec pegou a diferença). Entradas de navegação: `link-card` **📈 Histórico de Evoluções** no bloco de links do detalhe do paciente e botão homônimo no `page-header` de `paciente-sessao-list`. 77. Gráfico de evolução da dor no histórico de evoluções, fase 2/3 (issue #206). A linha do tempo entregue em #205 exige comparar `dorAntes`/`dorDepois` cartão por cartão para perceber se o paciente melhorou ao longo de semanas; o gráfico mostra a tendência de imediato e é o principal argumento da tela na conversa com o paciente. O desenho é **SVG inline** no próprio `paciente-evolucao-list`, sem nova dependência — o projeto não tem biblioteca de gráficos e o `simetrografo-editor` já monta SVG assim. Toda a matemática mora na função pura exportada `montarGraficoDor(itens)`, que recebe a mesma coleção derivada que alimenta a linha do tempo e devolve `GraficoDor | null`: **nenhuma requisição a mais** entra na carga da tela (o spec trava as três chamadas em `toHaveBeenCalledTimes(1)`). A lista é decrescente e o eixo X é cronológico crescente, então a função inverte a coleção-fonte em vez de reordenar — as duas vistas saem da mesma ordenação, sem lógica duplicada. Decisões que ficaram registradas em comentário no código: (a) o eixo Y é **fixo em 0–10**, a escala da dor no formulário de evolução, e não normalizado pelos valores presentes — normalizar faria uma variação de 4 para 5 parecer uma queda dramática; há um `clamp` defensivo para que um valor fora da escala não desenhe o ponto por cima dos rótulos. (b) Uma sessão com dor `null` **não vira ponto em `0`**: a série é quebrada em trechos e cada trecho contínuo com dois pontos ou mais vira um `<polyline>` próprio (`serie.linhas`), enquanto trechos de um ponto só ficam apenas como círculo — sem isso um `polyline` de um vértice seria invisível. (c) O gráfico não é renderizado enquanto **nenhuma série chega a dois pontos**: uma medição isolada não desenha tendência nenhuma, e a linha do tempo segue normal. (d) O eixo X reserva posição para **todas** as sessões da linha do tempo, inclusive as sem evolução: é o intervalo em que a dor não foi medida, e comprimi-lo distorceria o espaçamento. Só até 5 delas ganham data escrita (`indicesDasMarcasX`, sempre com a primeira e a última, e as das pontas ancoradas em `start`/`end` para não vazar do `viewBox`); acima de 30 sessões os círculos viram uma faixa sólida — e centenas de nós no DOM —, então só os pontos isolados seguem marcados. (e) As datas são formatadas a partir do prefixo ISO de `dataHora` (`dd/MM` no eixo, `dd/MM/yyyy` no `aria-label`) em vez de `new Date`: a string vem sem fuso e o construtor já viraria um dia a menos no rótulo. (f) As coordenadas são arredondadas a duas casas, o que basta na escala do `viewBox` e evita `26,64.20000000000002` no atributo `points`. Acessibilidade: o `<svg>` inteiro é um `role="img"` com `aria-label` textual ("Gráfico da evolução da dor ao longo de 2 sessões, de 01/05/2026 a 20/05/2026. Dor antes: de 7 em 01/05/2026 para 2 em 20/05/2026. Dor depois: …"), e grade, eixos e rótulos internos são `aria-hidden` — sem nome acessível eles seriam só ruído para o leitor de tela. As duas séries são nomeadas numa legenda `<figcaption>` e distinguidas por cor **e** por tracejado, para quem não separa âmbar de azul. As cores vêm de `--c-warning-text` (antes) e `--text-brand` (depois), os dois tokens com versão própria no tema escuro; a escolha é deliberadamente neutra, e não `--c-success`/`--c-danger`, porque a série "depois" não é necessariamente a boa notícia. Cada série publica a cor num custom property `--serie-cor` no `<g>`, o que faz o mesmo token pintar o `stroke` do SVG e a borda do quadradinho HTML da legenda sem repetir a lista de cores. O responsivo é `viewBox` + `preserveAspectRatio="xMidYMid meet"` com `width: 100%` e `max-width: 480px`: o desenho encolhe junto com a coluna e nunca empurra scroll horizontal, e o teto existe porque o texto dentro do SVG está em unidades do `viewBox` e cresceria junto com o desenho. Cobertura: 13 casos novos em `paciente-evolucao-list.component.spec.ts` (gráfico acima da linha do tempo; omitido com zero e com uma sessão com dor; pontos do mais antigo para o mais recente, inversos à lista; eixo Y em 0–10 independente dos valores; série quebrada em vez de ponto em `0`; `role`/`aria-label`; legenda nomeando as duas séries; nenhuma requisição extra; cor de cada série nos temas claro e escuro; `viewBox`/`preserveAspectRatio`/`max-width`; o teto de 5 marcas no eixo X com a primeira e a última sempre presentes; e a supressão dos marcadores num gráfico denso preservando o ponto isolado). Validação manual com o backend local: **nenhuma evolução da base real importada tem `dorAntes`/`dorDepois`** — como já registrado na fase 1, o único campo preenchido é `observacoesFisioterapeuta` —, então o cenário foi montado pela própria tela de evolução em Carolina Safadi (paciente 17, 7 sessões), com dor em 5 delas (8→6, 7→4, 5→3, 4→2, 3→1) e duas deixadas em branco de propósito. Conferidos: gráfico ausente com uma única sessão com dor e a linha do tempo intacta; as duas quebras de série com o ponto isolado do meio desenhado como círculo; `aria-label` completo no DOM; exatamente três requisições na carga da tela (paciente, sessões e evoluções — nenhuma por causa do gráfico); os dois temas; e 375px sem scroll horizontal. Dois ajustes saíram dessa validação: (a) num card de largura total o desenho ficava encostado à esquerda com um vazio à direita do mesmo tamanho, então o `figure` passou a ter `max-width` acompanhando o teto do SVG mais o padding; (b) os rótulos dos eixos subiram de 11 para 13 unidades do `viewBox` — em 375px o desenho encolhe para ~0,6 e os 11 rendiam ~6,6px na tela. Dois achados do review do PR foram corrigidos no mesmo ciclo, ambos com a mesma raiz — a guarda operava sobre **sessões com dor** em vez de **pontos por série**. (a) Quando `dorDepois` nunca era preenchida (cenário real: a fisioterapeuta que só registra a dor inicial), a legenda continuava anunciando **Dor depois** com o traço da cor enquanto nada era desenhado, contradizendo o `aria-label`, que já omitia a série. Séries sem nenhum ponto passaram a ser filtradas antes do desenho, o que remove de uma vez o `<g>` e o item da legenda. (b) Com uma sessão só com `dorAntes` e outra só com `dorDepois`, o total de sessões com dor chegava a dois e o gráfico renderizava eixos e legenda em volta de **dois pontos soltos, sem linha nenhuma** — atendia a letra do critério da issue e derrotava o propósito da tela. A guarda passou a exigir que ao menos uma série chegue a `GRAFICO_MIN_PONTOS_SERIE` pontos; a constante renomeada de `GRAFICO_MIN_SESSOES_COM_DOR` também virou a guarda explícita da divisão em `posicaoX`, que antes dependia do efeito colateral de o total de sessões nunca ser menor que o de sessões com dor. Cobertura dos achados: 2 casos novos (gráfico omitido quando nenhuma série chega a dois pontos, com as duas medições ainda legíveis nos cards; e série sem ponto fora do SVG, da legenda e do `aria-label`), verificados em navegador contra o código anterior nos dois cenários. Ficaram fora de escopo, como previsto na issue: filtros de período e tipo (fase 3, quando o gráfico passa a respeitá-los), gráficos de outras métricas, tooltip/zoom/exportação e qualquer biblioteca de gráficos.

78. Filtros de período e tipo de sessão no histórico de evoluções, fase 3/3 (issue #207). Com a linha do tempo (#205) e o gráfico (#206), a tela mostrava todo o tratamento de uma vez: um paciente de longa data rende dezenas de cards e um gráfico com dezenas de pontos, sem como recortar o mês que interessa antes de um atendimento nem separar as sessões de fisioterapia das de pilates. A barra de filtros — data inicial, data final e tipo (todos / pilates / fisioterapia) — fica no topo, acima do gráfico, e recorta **client-side** a coleção já carregada: o spec trava as três requisições da carga em `toHaveBeenCalledTimes(1)` depois de aplicar e limpar filtros, e a validação em navegador confirmou zero chamadas `/api/` em toda a sessão de filtragem. A decisão central é o recorte morar num **único ponto**: a função pura exportada `filtrarItens(itens, filtro)` produz `itens`, e é esse resultado que alimenta ao mesmo tempo o `*ngFor` da linha do tempo e `montarGraficoDor` — por construção não há como o gráfico plotar uma sessão que a lista não mostra, que é o critério central da issue. A fonte carregada passou a ficar em `itensCarregados`, preservada para o "limpar filtros" restaurar a coleção completa sem recarregar. Decisões registradas em comentário: (a) as datas são comparadas pelo prefixo ISO (`yyyy-MM-dd`) de `dataHora` contra os limites do `<input type="date">`, que já vêm nesse formato — a ordem lexicográfica coincide com a cronológica, o dia inteiro entra nas duas pontas (a sessão das 14h do dia final não pode cair fora) e nenhum `Date` é construído, o que reintroduziria o deslocamento de fuso que `formatarData` já evitava desde a fase 2; (b) o item da linha do tempo ganhou `tipoSessao` (o tipo cru) além do rótulo exibido, para o filtro não comparar contra strings traduzidas, e o select é montado a partir de `SESSAO_TIPO_LABEL` em vez de redeclarar as opções; (c) data final anterior à inicial é recorte **impossível**, não recorte vazio: exibe a mensagem no formulário e não aplica o período, mas mantém o filtro de tipo, que é independente — derrubá-lo junto surpreenderia quem só errou a data; (d) a regra do gráfico (menos de dois pontos numa série ⇒ sem desenho) passa a valer sobre o conjunto filtrado, então um recorte de uma sessão só esconde o gráfico e mantém a linha do tempo, verificado em navegador; (e) o recorte vazio tem estado próprio, com a ação **Limpar filtros** que a issue #146 pede para as listagens, distinto do "Nenhuma evolução registrada" de paciente sem histórico. A barra usa o grid `auto-fit`/`minmax(180px, 1fr)` dos filtros de `paciente-list` (empilha sozinho em 375px, sem media query) e os `.form-control` globais, o que traz a seta padronizada do issue #200 de graça. A validação em navegador rendeu um ajuste de acessibilidade: o `.invalid-feedback` global usa `--c-danger`, que também serve de fundo (`.btn-danger`) e por isso **não** é clareado no tema escuro — medido sobre a superfície elevada do card de filtros dava 2,12:1 em 11px. O `.filtro-erro` passou a usar `--c-danger-text`, a variante criada em `_tokens.scss` exatamente para texto sobre superfície elevada: idêntica no tema claro e 4,96:1 no escuro (medido no DOM). O `aria-describedby` dos dois campos é ligado por `[attr.]` e some junto com a mensagem, em vez de apontar para um id inexistente — o mesmo achado de referência quebrada que o review da fase 1 pegou no `aria-controls`. Cobertura: 19 casos novos em `paciente-evolucao-list.component.spec.ts` (barra acima do gráfico; label e id de cada campo mais as opções vindas do mapa de rótulos; período reduzindo lista e pontos de forma coerente; dia inteiro nas duas pontas; filtro por tipo nos dois tipos e o retorno em "todos"; período + tipo combinados; sessão realizada sem evolução respeitando os mesmos filtros; período invertido sem aplicar, com `role="alert"`, `aria-describedby` e `is-invalid`; erro limpo ao reordenar as datas; estado vazio do recorte com a ação de limpar; restauração da coleção completa pela barra, com o botão desabilitado sem filtro ativo; gráfico oculto quando o recorte deixa menos de dois pontos e de volta ao limpar; nenhuma requisição ao filtrar ou limpar; filtro aplicado pelo campo e pelo select renderizados; barra ausente quando não há o que filtrar; contraste da mensagem de erro nos dois temas; e o empilhamento em 375px sem overflow). Três desses guards foram verificados contra uma versão em que o gráfico deriva da coleção completa em vez do recorte, e falham. QA manual com o backend local em Carolina Safadi (paciente 17), que tinha 7 sessões de pilates entre dez/2025 e jan/2026 com dor em 5 delas; foram criadas mais duas sessões de fisioterapia com dor (09/12 e 13/01) para o cenário misto que a issue pede. ## Decisões Técnicas

### Angular 19 com Standalone Components
Todos os componentes são standalone (sem NgModules), seguindo a arquitetura moderna do Angular. Isso reduz boilerplate e melhora o tree-shaking. Os imports de cada componente usam apenas as diretivas e pipes necessários (`NgIf`, `NgFor`, `NgClass`, `DatePipe`, `CurrencyPipe` etc.), evitando a importação completa do `CommonModule` e favorecendo o tree-shaking.

### Design System por tokens
Os protótipos do Design System foram preservados em `assets/` para consulta e validação visual. O frontend Angular importa os tokens por `src/styles/_tokens.scss`, mantendo nomes semânticos para cores, tipografia, espaçamento, raios, sombras e densidade. A camada de componentes deve preferir esses tokens a valores hexadecimais ou medidas avulsas.

### Tema e densidade
Tema e densidade são parametrizados por atributos no elemento raiz: `data-theme` alterna as paletas clara e escura, enquanto `data-density` ajusta `--row-h`, `--input-h`, `--btn-h`, `--btn-h-sm` e `--gutter`. O `StylePreferencesService` (`core/services/style-preferences.service.ts`) centraliza a resolução, aplicação e persistência dessas preferências.

No startup, o serviço resolve a preferência inicial nesta ordem: (1) preferência salva em `localStorage` na chave `carlesso.style-preferences`; (2) na ausência de preferência salva, o tema segue `prefers-color-scheme` do sistema operacional via `matchMedia`, com densidade `default`. O valor resolvido pelo fallback é apenas aplicado ao DOM, **não** é persistido — assim a preferência do sistema continua valendo até o usuário escolher explicitamente um tema. Os métodos `setTheme`, `setDensity`, `apply` e `toggleTheme` gravam a preferência resultante em `localStorage`; falhas de acesso ao storage (modo privado, quota) são silenciadas e a preferência permanece apenas em memória.

O dark mode em si é definido inteiramente pelos tokens em `[data-theme="dark"]` (`src/styles/_tokens.scss`, espelhado em `assets/tokens.css`), que sobrescrevem superfícies (`--bg-*`), texto (`--text-*`), bordas (`--border-*`), sombras e fundos funcionais. Não há paleta paralela nem cores hardcoded específicas de tema na camada de componentes.

### Controle de tema na interface
A navbar do `AppComponent` expõe o botão **Tema claro/Tema escuro** (`.btn-tema`), agrupado com o botão **Sair** em `.navbar-actions`. A tela de login também expõe o mesmo controle visual por meio de `.login-theme-toggle`, permitindo alternar o tema antes da autenticação. Ambos chamam `StylePreferencesService.toggleTheme()` e expõem `aria-pressed` (estado do tema escuro) e `aria-label` descritivo da ação. A navbar continua aparecendo apenas quando o usuário está autenticado; a tela de login respeita e também pode alterar o tema persistido ou resolvido por `prefers-color-scheme`.

### Lazy Loading em todas as rotas
Cada componente de página é carregado sob demanda via `loadComponent()`, otimizando o bundle inicial.

### Reactive Forms
Formulários construídos com `FormBuilder` e `FormGroup` para controle granular de validação e estado.

### Soft Delete (Inativação e Reativação)
O backend não remove pacientes fisicamente. Inativação usa `PATCH /pacientes/{id}/inativar` e reativação usa `PATCH /pacientes/{id}/ativar`. A listagem exibe apenas pacientes ativos; o detalhe exibe qualquer status e oferece o botão correto (Ativar ou Inativar) conforme o estado atual do paciente.

### CPF imutável após cadastro
Por regra de negócio, o CPF não pode ser alterado após o cadastro. O formulário de edição desabilita apenas o campo CPF. O e-mail pode ser atualizado via `PUT /pacientes/{id}` e é incluído no `PacienteUpdateDTO`.

### Anamnese do paciente
A tela `/pacientes/:pacienteId/anamnese` usa Reactive Forms para criar ou editar a anamnese principal do paciente. O componente valida o parâmetro `pacienteId` com `parseRouteNumberParam`, carrega a identificação do paciente por `PacienteService.buscar` e tenta carregar a anamnese via `GET /api/anamneses/paciente/{pacienteId}`. Retorno `404` nessa consulta indica ausência de anamnese e mantém o formulário em modo de cadastro. O salvamento usa `POST /api/anamneses` quando ainda não há registro e `PUT /api/anamneses/{id}` quando a anamnese já existe. Os campos `queixaPrincipal` e `objetivos` são obrigatórios e rejeitam conteúdo somente com espaços, refletindo o contrato `@NotBlank` do backend.

### Avaliação Fisioterapêutica do paciente
A tela `/pacientes/:pacienteId/avaliacao-fisioterapeutica` usa Reactive Forms para criar ou editar a avaliação fisioterapêutica do paciente. O componente valida o parâmetro `pacienteId` com `parseRouteNumberParam`, carrega a identificação do paciente por `PacienteService.buscar` e lista as avaliações via `GET /api/avaliacoes-fisioterapeuticas/paciente/{pacienteId}`. O backend retorna uma lista ordenada por `dataAvaliacao` e ID em ordem decrescente; a tela edita a avaliação mais recente quando há itens e mantém o formulário em modo de cadastro quando a lista vem vazia. O salvamento usa `POST /api/avaliacoes-fisioterapeuticas` com `pacienteId` quando ainda não há registro carregado e `PUT /api/avaliacoes-fisioterapeuticas/{id}` quando já existe. Os campos `dataAvaliacao`, `queixaFuncional`, `escalaDor` e `diagnosticoFisioterapeutico` são obrigatórios; `queixaFuncional` e `diagnosticoFisioterapeutico` rejeitam conteúdo somente com espaços, e `escalaDor` deve ficar entre 0 e 10. Demais campos — `avaliacaoPostural`, `mobilidadeArticular`, `forcaMuscular`, `flexibilidade`, `equilibrio`, `coordenacaoMotora`, `padraoRespiratorio`, `testesFuncionaisRealizados` e `observacoesGerais` — são opcionais.

### Sessões de Pilates/Fisioterapia do paciente
A tela `/pacientes/:pacienteId/sessoes` lista as sessões de pilates ou fisioterapia vinculadas ao paciente. O componente valida `pacienteId` com `parseRouteNumberParam`, carrega a identificação do paciente por `PacienteService.buscar` e consulta as sessões por `GET /api/sessoes/paciente/{pacienteId}`. A rota `/pacientes/:pacienteId/sessoes/nova` cria uma sessão por `POST /api/sessoes` com `pacienteId`; a rota `/pacientes/:pacienteId/sessoes/:id/editar` carrega a sessão por `GET /api/sessoes/{id}`, valida que `sessao.pacienteId` corresponde ao paciente da rota e salva alterações via `PUT /api/sessoes/{id}`. O `PUT` aplica somente `dataHora` (desmembrado em `data`/`horario`), `duracao` e `observacoes`; por isso, na edição, os campos **Tipo**, **Profissional** e **Status** são exibidos desabilitados, apenas como informação, cada um com um hint explicando por quê. Tipo e profissional são definidos no agendamento (`POST /api/sessoes`) e o status muda apenas pelas ações Realizar/Cancelar da listagem. A listagem permite marcar sessões agendadas como realizadas por `PATCH /api/sessoes/{id}/realizar` e cancelar sessões agendadas por `PATCH /api/sessoes/{id}/cancelar`, sempre com confirmação antes da chamada. Os campos de UI `dataHora`, `tipo` e `duracao` são obrigatórios; o serviço converte `dataHora` em `data` e `horario`, envia `duracao` como `duracaoMinutos` e normaliza a resposta da API de volta para o modelo usado pelos componentes. `duracao` deve ficar entre 1 e 480 minutos. O tipo pode ser `PILATES` ou `FISIOTERAPIA`. O status é exibido como `AGENDADA`, `REALIZADA` ou `CANCELADA` com labels centralizados em `SESSAO_STATUS_LABEL`.

### Evolução de Sessão do paciente
A tela `/pacientes/:pacienteId/sessoes/:sessaoId/evolucao` permite registrar e editar a evolução clínica de uma sessão específica de pilates ou fisioterapia. O componente valida `pacienteId` e `sessaoId` com `parseRouteNumberParam`, carrega o paciente por `PacienteService.buscar`, carrega a sessão por `SessaoService.buscar` e só consulta a evolução depois de validar que `sessao.pacienteId` corresponde ao paciente da rota. A evolução é carregada por `GET /api/evolucoes-sessao/sessao/{sessaoId}`; retorno `404` nessa consulta indica ausência de evolução e mantém o formulário em modo de cadastro. O salvamento usa `POST /api/evolucoes-sessao` com `sessaoId` quando ainda não há registro e `PUT /api/evolucoes-sessao/{id}` quando já existe. O campo `dataHoraRegistro` é obrigatório. Os campos `exerciciosRealizados`, `equipamentosUtilizados`, `cargasMolas`, `respostaPaciente`, `intercorrencias`, `orientacoes` e `observacoesFisioterapeuta` são opcionais. `dorAntes` e `dorDepois`, quando informados, devem ficar entre 0 e 10. A listagem de sessões exibe um botão **Evolução** para cada sessão, navegando para a rota de evolução correspondente.

### Histórico de Evoluções do paciente
A tela `/pacientes/:pacienteId/evolucoes` (`PacienteEvolucaoListComponent`) é a **segunda forma de leitura** das evoluções: uma linha do tempo somente leitura com todas as evoluções do paciente numa única página, da mais recente para a mais antiga. A tela de cadastro/edição por sessão continua sendo a única forma de escrever evolução — nenhum `POST`/`PUT` sai daqui. O componente valida `pacienteId` com `parseRouteNumberParam`, carrega a identificação do paciente por `PacienteService.buscar` e então dispara um `forkJoin` de `SessaoService.listarPorPaciente` (`GET /api/sessoes/paciente/{id}`) e `EvolucaoSessaoService.listarPorPaciente` (`GET /api/evolucoes-sessao/paciente/{id}`), cruzando as duas listas no cliente por `sessaoId`. As duas requisições existem porque o `EvolucaoSessaoResponseDTO` não traz data/tipo/profissional da sessão; desnormalizá-lo economizaria uma chamada, mas a tela deixaria de conhecer as sessões **sem** evolução. Entram na linha do tempo as sessões com evolução, as sessões `REALIZADA` ainda sem evolução (marcadas como **Sem evolução registrada**, com link para registrar) e — defensivamente — evoluções cuja sessão não veio na listagem, que de outra forma sumiriam do prontuário. Sessões `AGENDADA` e `CANCELADA` sem evolução ficam de fora. A ordenação é por data/hora da sessão em ordem decrescente, com desempate por `sessaoId`. O cabeçalho de cada card traz data/hora, tipo, profissional e a variação `dorAntes → dorDepois` com indicação de melhora/piora pelos tokens `--c-success-text`/`--c-danger-text`; o corpo mantém **Observações do fisioterapeuta** sempre visível (é o campo mais lido — ver #204, e na base real é o único preenchido) e os demais campos atrás de um botão com `aria-expanded`/`aria-controls`, com **Expandir tudo**/**Recolher tudo** no topo da lista. O par de dor expõe um `aria-label` próprio ("Dor antes 7, depois 3, melhora"), já que o `→` é decorativo, e o valor ausente cai para `—`. O painel de detalhes fica sempre no DOM quando há campos colapsáveis — escondido pela classe `.evolucao-detalhes-recolhido`, no mesmo padrão dos filtros de `paciente-list` — para que o `aria-controls` do botão sempre resolva. Campos vazios não são renderizados. Os erros das duas cargas usam `extrairMensagemErro`, e a falha do `forkJoin` exibe uma mensagem neutra ("Não foi possível carregar o histórico de evoluções."), porque quem falhou pode ter sido a listagem de sessões. A lista derivada (`itens`) fica num único ponto do componente, para que o gráfico de dor e o recorte dos filtros de período/tipo consumam a mesma coleção.

Acima da linha do tempo, a tela desenha o **gráfico da evolução da dor** (#206): um SVG inline montado pela função pura `montarGraficoDor(itens)`, sem biblioteca de gráficos e sem requisição própria — ele deriva da mesma coleção `itens`, invertida, porque a lista é decrescente e o eixo X é cronológico crescente. O eixo Y é fixo em 0–10 (a escala do formulário de evolução), e não normalizado pelos valores presentes. O eixo X reserva uma posição para cada sessão da linha do tempo, inclusive as sem evolução, e escreve a data de no máximo cinco delas — sempre a primeira e a última, ancoradas para dentro do `viewBox`. Uma sessão com dor `null` **não** vira ponto em `0`: a série é quebrada em trechos, cada trecho contínuo de dois pontos ou mais vira um `<polyline>` e trechos de um ponto só ficam como círculo. O gráfico não é renderizado enquanto **nenhuma série chega a dois pontos** — o critério é por série, e não o total de sessões com dor: duas medições em séries diferentes não se ligam e renderizariam eixos e legenda em volta de dois pontos soltos. Séries sem nenhum ponto são descartadas antes do desenho, de modo que a legenda nunca anuncia uma linha que não existe. Nos dois casos a linha do tempo segue normal. Acima de 30 sessões os círculos deixam de ser desenhados, exceto os pontos isolados: a linha basta, e o resto viraria uma faixa sólida com centenas de nós no DOM. O `<svg>` inteiro é um `role="img"` com `aria-label` textual (número de sessões, período e a primeira e a última medição de cada série), com grade, eixos e rótulos internos em `aria-hidden`; as duas séries são nomeadas numa legenda e distinguidas por cor e por tracejado, com `--c-warning-text` (antes) e `--text-brand` (depois) — neutras de propósito, porque a série "depois" não é necessariamente a boa notícia. O responsivo vem de `viewBox` + `preserveAspectRatio` com `width: 100%` e `max-width: 480px`, sem gerar scroll horizontal. As observações usam `white-space: pre-wrap`: o texto vem da API em blocos de queixas e conduta, e o HTML colapsaria as quebras num parágrafo só. O card usa `--bg-elev` e `--text-brand`, e **não** os `--surface`/`--c-primary` das demais listagens do prontuário — esses dois tokens nunca foram definidos em `_tokens.scss`, de modo que lá o fundo do card não é pintado e a borda de destaque cai para `currentColor`. Paginação, filtros server-side, gráfico, exportação e edição inline ficaram fora de escopo.

No topo da tela, acima do gráfico, uma barra de **filtros de período e tipo de sessão** (#207) recorta o histórico: data inicial, data final e um select de tipo (todos / pilates / fisioterapia) alimentado por `SESSAO_TIPO_LABEL`. O recorte é **client-side** sobre a coleção já carregada — nenhuma requisição sai da tela ao alterar ou limpar filtros — e é calculado num único ponto, a função pura `filtrarItens(itensCarregados, filtro)`, cujo resultado (`itens`) alimenta ao mesmo tempo a linha do tempo e `montarGraficoDor`: por construção não há como o gráfico plotar uma sessão que a lista não mostra. A fonte carregada fica preservada em `itensCarregados` para o "limpar filtros" voltar a ela. A comparação de datas usa o prefixo ISO (`yyyy-MM-dd`) de `dataHora` contra os limites do `<input type="date">`, que já vêm nesse formato: a ordem lexicográfica coincide com a cronológica, o dia inteiro entra nas duas pontas e nenhum `Date` é construído — o que reintroduziria o deslocamento de fuso que `formatarData` já evita. O item da linha do tempo passou a carregar `tipoSessao` (o tipo cru) além do rótulo exibido, para o filtro não comparar strings traduzidas. Data final anterior à inicial é recorte impossível, não recorte vazio: a mensagem aparece no formulário (`role="alert"`, `aria-describedby` nos dois campos, `is-invalid` nas bordas) e o período **não** é aplicado; o filtro de tipo, independente, continua valendo — derrubá-lo junto surpreenderia quem só errou a data. A regra do gráfico passa a valer sobre o conjunto filtrado, então um recorte que deixa menos de dois pontos numa série esconde o desenho e mantém a linha do tempo. O recorte sem resultados tem estado vazio próprio, com ação **Limpar filtros** (issue #146), distinto do "Nenhuma evolução registrada" de paciente sem histórico. A barra usa o mesmo grid `auto-fit`/`minmax(180px, 1fr)` dos filtros de `paciente-list`, que empilha sozinho em 375px sem media query, e os `.form-control` globais; no mobile ela fica atrás do disclosure do issue #163, como nas outras duas listagens com filtro, e um `<p role="status">` permanente logo abaixo anuncia o tamanho do recorte para o leitor de tela. A única exceção ao padrão global é a cor da mensagem de erro: o `.invalid-feedback` usa `--c-danger`, que também serve de fundo (`.btn-danger`) e por isso não é clareado no tema escuro — sobre a superfície elevada do card de filtros rende 2,1:1 em 11px, então o `.filtro-erro` usa `--c-danger-text`, a variante criada exatamente para esse caso (idêntica no tema claro, 5,0:1 no escuro). Ficaram fora de escopo: filtros server-side, persistência do filtro na URL ou em `localStorage`, atalhos de período pré-definido e filtros por profissional, faixa de dor ou intercorrências.

### Plano de Tratamento do paciente
A tela `/pacientes/:pacienteId/plano-tratamento` lista os planos de tratamento vinculados ao paciente. O componente valida `pacienteId` com `parseRouteNumberParam`, carrega a identificação do paciente por `PacienteService.buscar` e consulta os planos por `GET /api/planos-tratamento/paciente/{pacienteId}`. A rota `/pacientes/:pacienteId/plano-tratamento/novo` cria um plano por `POST /api/planos-tratamento` com `pacienteId`; a rota `/pacientes/:pacienteId/plano-tratamento/:id/editar` carrega o plano por `GET /api/planos-tratamento/{id}`, valida que `plano.pacienteId` corresponde ao paciente da rota e salva alterações via `PUT /api/planos-tratamento/{id}`. A listagem permite suspender planos ativos por `PATCH /api/planos-tratamento/{id}/suspender` e encerrar planos ativos ou suspensos por `PATCH /api/planos-tratamento/{id}/encerrar`, sempre com confirmação antes da chamada. Os campos `dataInicio`, `objetivosTerapeuticos`, `frequenciaSemanal`, `condutasPropostas` e `exerciciosIndicados` são obrigatórios; os textos obrigatórios rejeitam valores somente com espaços e `frequenciaSemanal` deve ficar entre 1 e 7. O status é exibido como `ATIVO`, `ENCERRADO` ou `SUSPENSO` com labels centralizados em `PLANO_TRATAMENTO_STATUS_LABEL`.

### Reavaliações do paciente
A tela `/pacientes/:pacienteId/reavaliacoes` lista as reavaliações periódicas vinculadas ao paciente. O componente valida `pacienteId` com `parseRouteNumberParam`, carrega a identificação do paciente por `PacienteService.buscar` e consulta as reavaliações por `GET /api/reavaliacoes/paciente/{pacienteId}`. A rota `/pacientes/:pacienteId/reavaliacoes/nova` cria uma reavaliação por `POST /api/reavaliacoes` com `pacienteId`; a rota `/pacientes/:pacienteId/reavaliacoes/:id/editar` carrega a reavaliação por `GET /api/reavaliacoes/{id}`, valida que `reavaliacao.pacienteId` corresponde ao paciente da rota e salva alterações via `PUT /api/reavaliacoes/{id}`. O único campo obrigatório é `dataReavaliacao`; os demais — `comparativoAvaliacaoAnterior`, `evolucaoDor`, `evolucaoForca`, `evolucaoMobilidade`, `evolucaoFuncional`, `objetivosAlcancados`, `pontosAtencao`, `ajustesPlanoTratamento` e `observacoesGerais` — são opcionais. Após criação bem-sucedida o formulário navega para a listagem; após atualização exibe mensagem de sucesso e permanece na tela.

### NFSEs emitidas do paciente
A tela `/pacientes/:pacienteId/nfse-emitidas` (`PacienteNfseEmitidaListComponent`) lista as NFSEs emitidas persistidas para o paciente. O componente valida `pacienteId` com `parseRouteNumberParam`, carrega a identificação do paciente por `PacienteService.buscar` e consulta as notas por `GET /api/api/nfse-emitidas/paciente/{pacienteId}`. As notas são ordenadas por `dataEmissao` decrescente e a getter `ultimaNota` expõe a NFSE mais recente, exibida em destaque no topo da listagem. Pacientes sem nota registrada veem um estado vazio explícito, e falhas de carregamento exibem mensagem amigável.

As rotas `/pacientes/:pacienteId/nfse-emitidas/nova` e `/pacientes/:pacienteId/nfse-emitidas/:id/editar` (`PacienteNfseEmitidaFormComponent`) registram ou atualizam a NFSE emitida via `POST /api/api/nfse-emitidas` (o backend faz upsert por paciente/competência). Os campos obrigatórios são `competencia` (formato `MM/AAAA`, mês entre `01` e `12`) e `dataEmissao`; os opcionais `numeroNota` (máx. 60 caracteres), `valor` (≥ 0) e `observacoes` são sanitizados — strings vazias viram `null` e o valor é convertido com `Number.isFinite` para número ou `null`. Como o backend não expõe busca de NFSE por ID, o modo de edição localiza a nota pela listagem do paciente (`listarPorPaciente`), validando que o `id` pertence ao paciente da rota e pré-preenchendo o formulário (estado vazio/“não encontrada” tratado). Após sucesso o formulário navega para a listagem. Cada card da listagem oferece a ação **Editar**. O `NfseEmitidaService` usa o prefixo `/api/api/nfse-emitidas` pelo mesmo motivo do `RelatorioService`: o backend expõe o recurso em `/api/nfse-emitidas` e o proxy de desenvolvimento e o Nginx removem o primeiro prefixo `/api`. A tela de detalhe do paciente oferece o card **NFSEs Emitidas** para acesso rápido.

O tratamento de erro de ambas as telas usa o utilitário `extrairMensagemErro` (`shared/utils/api-error.ts`), que respeita o contrato de erro do backend: `401`/`403` exibem mensagem de sessão/autorização, `429` exibe mensagem de excesso de requisições, e demais status (`400`/`409`/`422`) usam `message`/`error`/`detail` do corpo ou a junção das mensagens de erro por campo, caindo numa mensagem genérica quando não há texto aproveitável.

### Atualização de profissionais via PUT
O cadastro de profissionais segue o contrato do backend para atualização via `PUT /profissionais/{id}` com `ProfissionalUpdateDTO`. Ativação e inativação continuam usando endpoints específicos com `PATCH`.

### Confirmação de aulas com profissional
A confirmação de presença em aulas usa `PATCH /aulas/{id}/realizar?profissionalId={id}`. O frontend carrega profissionais ativos via `GET /profissionais?page=0&size=100&sort=nome`, exige seleção antes de confirmar e exibe o profissional retornado em aulas já realizadas. Antes do `PATCH`, o `AulaListComponent` abre o `ConfirmarDialogComponent` compartilhado exibindo a data e o profissional selecionado, protegendo o vínculo (que não tem desfazer na UI) contra cliques acidentais, e mantém o estado `acaoEmAndamento` bindado no input `processando` para evitar duplo disparo. Se o usuário aciona **Marcar como Realizada** sem escolher profissional, o `select` da linha é destacado com `is-invalid`/`aria-invalid` e uma mensagem `invalid-feedback` em vez de a ação falhar em silêncio. Quando não há profissionais ativos, além de o botão ficar desabilitado, um `field-hint` orienta "Cadastre um profissional ativo para confirmar aulas". Cada `select` de profissional recebe `aria-label` descritivo com a data da aula ("Profissional responsável pela aula de {data}").

A listagem é responsiva ao celular (issue #155): a tabela fica dentro de um `div.table-wrap` (`overflow-x: auto`) para conter o scroll no card e, abaixo de 640px, uma media query no `aula-list.component.scss` a converte em cards por aula (um `tr` por card, `td` empilhados com rótulo via `data-label`/`::before`, `select` e botão de ação em largura total), evitando o vazamento horizontal da página em viewports de 375px/414px. É uma mudança apenas de template/CSS: os dados, o serviço e o fluxo de confirmação permanecem os mesmos.

### Relatório de pagamento de profissional
O relatório usa `GET /profissionais/{id}/relatorio-pagamento?inicio=YYYY-MM-DD&fim=YYYY-MM-DD`. A tela valida seleção de profissional, datas obrigatórias e impede consulta quando a data inicial é posterior à final. O retorno usa o contrato estruturado da API com `profissional`, `periodo`, `resumo`, `pagamentos`, `aulas` e `geradoEm`, consolidando total de aulas, total devido, agrupamento por pagamento e detalhamento por aula.

A exportação usa os endpoints `GET /profissionais/{id}/relatorio-pagamento/pdf?inicio=YYYY-MM-DD&fim=YYYY-MM-DD` e `GET /profissionais/{id}/relatorio-pagamento/xlsx?inicio=YYYY-MM-DD&fim=YYYY-MM-DD`. O frontend solicita a resposta como `Blob`, observa os headers HTTP, usa o nome retornado em `Content-Disposition` quando disponível e bloqueia os botões de exportação durante a geração do arquivo.

### Relatório de emissão de NFSEs
O relatório usa o endpoint do backend `GET /api/relatorios/nfse?competencia=MM/AAAA`, com filtro opcional `notaAnteriorEmitida=true|false`. Como o proxy de desenvolvimento e o Nginx removem o primeiro prefixo `/api` das chamadas do frontend, o `RelatorioService` chama `/api/api/relatorios/nfse` para encaminhar ao backend como `/api/relatorios/nfse`. A tela exige competência no formato `MM/AAAA`, valida mês entre `01` e `12`, exibe total de registros, soma de valores pagos e lista os campos `nome`, `cpfCnpj`, `valorPago`, `competencia`, `descricaoServico`, `notaAnteriorEmitida`, `dataPagamento` e `observacoes`. A partir da issue de backend #38, o campo `notaAnteriorEmitida` reflete a NFSE emitida persistida do paciente (ver **NFSEs emitidas do paciente**) em vez de uma inferência por pagamento anterior; o contrato do `RelatorioNfseResponseDTO` e o fluxo da tela permanecem inalterados.

A exportação usa o mesmo endpoint com `formato=CSV` ou `formato=XLSX`. O frontend trata a resposta como `Blob`, preserva o nome de arquivo retornado em `Content-Disposition` quando disponível e aplica fallback `relatorio-nfse-MM-AAAA.csv|xlsx`.

### Dashboard inicial
O dashboard inicial usa `GET /api/dashboard/resumo`, que o proxy local e o Nginx encaminham para `GET /dashboard/resumo` no backend. A tela exibe os indicadores principais em cards: pacientes ativos, profissionais ativos, receita confirmada do mês e aulas do mês atual. Também detalha pagamentos pendentes, pagos e vencidos, além de mostrar a proporção de aulas realizadas versus agendadas no mês corrente.

O retorno esperado segue o contrato `DashboardResumoDTO`, com grupos `pacientes`, `profissionais`, `pagamentos`, `aulas` e o timestamp `geradoEm`. O componente trata carregamento e falha de consulta com mensagens dedicadas, sem tentar reconstruir os indicadores por múltiplas chamadas de listagem.

### Seção administrativa
A seção administrativa fica em `pages/admin/` e é acessada por `/admin`, protegida por `roleGuard(['ADMIN'])`. O `AdminHomeComponent` serve como hub inicial e expõe links para os fluxos administrativos disponíveis. As rotas de usuários (`/admin/usuarios`, `/admin/usuarios/novo`, `/admin/usuarios/:id/editar`) também exigem `ADMIN`. A navbar exibe o link **Administração** apenas para usuários com perfil `ADMIN`. O `UsuarioFormComponent` valida o parâmetro `id` da rota com `parseRouteNumberParam` para alternar entre os modos de cadastro e edição e exibir **Identificador inválido.** quando o parâmetro não é um inteiro positivo seguro.

### Listagem administrativa de usuários
A tela `/admin/usuarios` (`UsuarioListComponent`) consome `UsuarioAdminService.listar` com paginação server-side, sincroniza `currentPage` e `pageSize` com os metadados de `Page<UsuarioAdminResponseDTO>` e renderiza no máximo 5 botões de página simultâneos (mesmo padrão da listagem de profissionais). A tabela exibe nome, e-mail, perfil (renderizado pelo label de `ROLE_OPTIONS`) e status (`Ativo`/`Inativo`/`—` quando o campo `active` não vier preenchido). O cabeçalho traz o botão **+ Novo Usuário** que navega para `/admin/usuarios/novo`; cada linha tem **Editar** (rota `/admin/usuarios/:id/editar`), **Inativar** ou **Reativar** (escolhido conforme o campo `active`, chamando `PATCH /api/users/{id}/inativar` ou `PATCH /api/users/{id}/ativar`) e **Excluir** (`DELETE /api/users/{id}`). Toda ação destrutiva (inativar, reativar, excluir) abre um diálogo de confirmação antes do disparo da requisição. Os botões de inativar/excluir ficam desabilitados para o próprio usuário logado (consultado via `AuthService.getCurrentUser()`), refletindo as regras de segurança do backend. A tela trata loading, mensagem de erro e estado vazio. Após inativar, reativar ou excluir o último item de uma página, o componente recua automaticamente para a página anterior válida.

### Service de usuários administrativos
O `UsuarioAdminService` centraliza todas as chamadas HTTP para `/api/users`. Os models em `core/models/usuario-admin.ts` definem `UsuarioAdminResponseDTO`, `UsuarioAdminCreateRequestDTO`, `UsuarioAdminUpdateRequestDTO`, `RoleOption` e `ROLE_OPTIONS`. O tipo `UserRole` é reutilizado de `auth.ts`; o tipo `Page<T>` é reutilizado de `paciente.ts`. O service segue o padrão dos demais services do projeto: `@Injectable({ providedIn: 'root' })`, injeção de `HttpClient`, URLs relativas `/api/*` e métodos em português (`listar`, `buscar`, `buscarPerfil`, `cadastrar`, `atualizar`, `excluir`, `ativar`, `inativar`, `listarRoles`, `alterarSenha`). O método `alterarSenha(dto: AlterarSenhaRequestDTO)` envia `PUT /api/users/me/senha` com o payload `{ senhaAtual, novaSenha, confirmacaoNovaSenha }` e é usado pelo `AlterarSenhaComponent`.

### Troca de senha do usuário autenticado
A tela `/perfil/alterar-senha` (`AlterarSenhaComponent`) permite que o usuário logado altere a própria senha. O componente é standalone, importa apenas `ReactiveFormsModule` e `RouterLink` e usa Reactive Forms com três controles obrigatórios: `senhaAtual`, `novaSenha` (mínimo de 8 caracteres) e `confirmacaoNovaSenha`. Dois validadores de grupo garantem que (1) `confirmacaoNovaSenha` coincida com `novaSenha` (erro `naoConfere`) e (2) `novaSenha` seja diferente de `senhaAtual` (erro `igualAtual`). Cada campo de senha tem um botão de toggle de visibilidade com `aria-pressed` e `aria-label` que alterna o `type` entre `password` e `text` sem afetar o valor do controle. O submit chama `UsuarioAdminService.alterarSenha`; respostas com código/campo explícito de `senhaAtual` exibem "Senha atual incorreta." e marcam o controle `senhaAtual` com erro `incorreta`; `401`/`403` sem esse sinal exibem mensagem de autorização/sessão; `400` propaga `err.error.message` quando disponível ou cai em "Dados inválidos para troca de senha."; outros erros usam "Erro ao alterar a senha. Tente novamente.". Após sucesso, o componente exibe mensagem de confirmação, limpa o formulário, chama `AuthService.clearSession()` e redireciona para `/login` (com um pequeno atraso para o usuário visualizar a mensagem). A flag `salvando` evita disparos duplicados. O link **Alterar senha** aparece na navbar (`AppComponent`) para todo usuário autenticado, ao lado dos botões de tema e de logout; em telas estreitas, as ações da navbar quebram linha para evitar overflow.

### Autorização por role
O `roleGuard` é uma factory function que recebe um array de `UserRole` permitidos e retorna um `CanActivateFn`. Ele verifica primeiro se o usuário está autenticado (token em `localStorage`); caso contrário redireciona para `/login`. Em seguida valida o role do usuário logado; quando o token existe mas `currentUser` está ausente ou inválido, a sessão local é limpa e o usuário volta para `/login`. Usuário autenticado sem o perfil exigido é redirecionado para `/403`. A tela `/403` (`ForbiddenComponent`) exibe código 403, mensagem orientativa e duas ações: link primário **Ir para o início** (`/`) e botão secundário **Voltar** que usa `Location.back()` quando há histórico do navegador (`window.history.length > 1`) e cai para `/` caso contrário, evitando que o usuário saia da SPA em deep links. Não acessa nenhum serviço externo. As rotas de `profissionais` e `relatorios` exigem `ADMIN`; as demais rotas continuam protegidas apenas pelo `authGuard`. Os links da navbar para `Profissionais` e `Relatórios`, além da ação de relatórios no dashboard, aparecem apenas para usuários administradores.

### Autenticação JWT
O frontend implementa autenticação stateless via JWT consumindo `POST /api/auth/login`. O retorno esperado contém `accessToken`, `tokenType` e o objeto `user` com os campos `id`, `name`, `email`, `role` e `active` opcional. O token é armazenado em `localStorage` pela `AuthService` sob a chave `accessToken`. Além do token, o `AuthService` armazena o objeto do usuário logado como JSON na chave `currentUser`. O método `getCurrentUser()` recupera esses dados tipados como `AuthenticatedUser`; retorna `null` quando não há sessão, o JSON armazenado está corrompido ou o formato não contém os campos obrigatórios. Os métodos `getCurrentUserRole()`, `isAdmin()` e `hasRole(role)` centralizam consultas de perfil. O `authInterceptor` (functional interceptor) injeta o header `Authorization: Bearer <token>` em todas as requisições, exceto no próprio endpoint de login. O interceptor só executa logout quando a resposta `401` indica explicitamente que o token é inválido ou expirou — via cabeçalho `WWW-Authenticate: Bearer error="invalid_token"` (ou `expired_token`) ou via corpo com `code` em `{TOKEN_EXPIRED, INVALID_TOKEN, TOKEN_INVALID}` — e somente quando há sessão ativa. Demais respostas `401` (por exemplo, rota inexistente que o Spring Security devolve como `401`, ou falhas pontuais do backend) são propagadas ao componente, que decide como exibir o erro, sem derrubar a sessão do usuário. O `authGuard` (functional guard) protege todas as rotas autenticadas e redireciona para `/login` quando não há token. O `AppComponent` exibe a navbar e o botão **Sair** apenas quando o usuário está autenticado, e exibe links administrativos apenas para `ADMIN`. O logout remove o token e os dados do usuário e redireciona para `/login`. O controle de acesso por perfil está implementado via `roleGuard` e a tela `/403` está disponível.

O `forbiddenInterceptor` complementa o `authInterceptor` tratando as respostas `403` da API (usuário autenticado, sem permissão para o recurso) sem derrubar a sessão e somente quando há sessão ativa — nos fluxos públicos (login, esqueci/redefinir senha) o `403` é propagado para a tela tratar: `403` em `GET` (carregamento de dados de uma tela) redireciona para `/403`; `403` nos demais métodos (ação pontual) exibe a mensagem padrão de acesso negado no banner global do `AppComponent`, alimentado pelo `NotificacaoService` e limpo a cada navegação, mantendo o usuário na tela. Requisições cujo `403` já é tratado pela própria tela marcam o `HttpContextToken` `TRATA_403_LOCALMENTE` para desligar o tratamento global e evitar mensagem duplicada.

### Proxy de desenvolvimento para CORS
O browser bloqueia requisições cross-origin de `localhost:4200` para `localhost:8080`. A solução adotada foi o proxy do Angular CLI: `proxy.conf.json` redireciona `/api/*` para `http://localhost:8080/*` no lado do servidor, eliminando o problema de CORS em desenvolvimento. O `PacienteService` usa a URL relativa `/api/pacientes`.

### Docker com Nginx
A imagem Docker usa build multi-stage: `node:22-alpine` instala dependências e executa `npm run build`; `nginx:1.27-alpine` serve o conteúdo de `dist/carlessopilatesfe/browser`.

O Nginx mantém o mesmo contrato de URL relativa do frontend:

- `/` serve a SPA com fallback para `index.html`
- `/api/*` é redirecionado para `${BACKEND_URL}/*`

O valor padrão de `BACKEND_URL` é `http://host.docker.internal:8080`, adequado para backend rodando na máquina host durante desenvolvimento local com Docker Compose. Em ambientes integrados, a variável deve apontar para o serviço real da API.

A configuração por `environment.ts` ainda não é necessária porque o frontend continua usando URLs relativas e o alvo da API é resolvido no proxy.

## Relacionamento com o Backend

A API segue o padrão REST. O frontend espera os seguintes contratos:

- `GET /pacientes?page=0&size=10&sort=nome` → `Page<PacienteResponseDTO>`
- `GET /pacientes?page=0&size=10&sort=nome&nome=&email=&cpf=&telefone=&ativo=true` → `Page<PacienteResponseDTO>`
- `GET /pacientes/{id}` → `PacienteResponseDTO`
- `POST /pacientes` (body: `PacienteRequestDTO`) → `PacienteResponseDTO`
- `PUT /pacientes/{id}` (body: `PacienteUpdateDTO`) → `PacienteResponseDTO`
- `PATCH /pacientes/{id}/inativar` → `204 No Content`
- `PATCH /pacientes/{id}/ativar` → `204 No Content`
- `POST /anamneses` (body: `AnamneseRequestDTO`) → `AnamneseResponseDTO`
- `GET /anamneses/{id}` → `AnamneseResponseDTO`
- `GET /anamneses/paciente/{pacienteId}` → `AnamneseResponseDTO`
- `PUT /anamneses/{id}` (body: `AnamneseUpdateDTO`) → `AnamneseResponseDTO`
- `POST /avaliacoes-fisioterapeuticas` (body: `AvaliacaoFisioterapeuticaRequestDTO`) → `AvaliacaoFisioterapeuticaResponseDTO`
- `GET /avaliacoes-fisioterapeuticas/paciente/{pacienteId}` → `AvaliacaoFisioterapeuticaResponseDTO[]`
- `PUT /avaliacoes-fisioterapeuticas/{id}` (body: `AvaliacaoFisioterapeuticaUpdateDTO`) → `AvaliacaoFisioterapeuticaResponseDTO`
- `GET /planos-tratamento/paciente/{pacienteId}` → `PlanoTratamentoResponseDTO[]`
- `GET /planos-tratamento/{id}` → `PlanoTratamentoResponseDTO`
- `POST /planos-tratamento` (body: `PlanoTratamentoRequestDTO`) → `PlanoTratamentoResponseDTO`
- `PUT /planos-tratamento/{id}` (body: `PlanoTratamentoUpdateDTO`) → `PlanoTratamentoResponseDTO`
- `PATCH /planos-tratamento/{id}/encerrar` → `PlanoTratamentoResponseDTO`
- `PATCH /planos-tratamento/{id}/suspender` → `PlanoTratamentoResponseDTO`
- `GET /sessoes/paciente/{pacienteId}` → `SessaoResponseDTO[]`
- `GET /sessoes/{id}` → `SessaoResponseDTO`
- `POST /sessoes` (body: `SessaoRequestDTO`) → `SessaoResponseDTO`
- `PUT /sessoes/{id}` (body: `SessaoUpdateDTO`) → `SessaoResponseDTO`
- `PATCH /sessoes/{id}/realizar` → `SessaoResponseDTO`
- `PATCH /sessoes/{id}/cancelar` → `SessaoResponseDTO`
- `GET /evolucoes-sessao/sessao/{sessaoId}` → `EvolucaoSessaoResponseDTO`
- `POST /evolucoes-sessao` (body: `EvolucaoSessaoRequestDTO`) → `EvolucaoSessaoResponseDTO`
- `PUT /evolucoes-sessao/{id}` (body: `EvolucaoSessaoUpdateDTO`) → `EvolucaoSessaoResponseDTO`
- `GET /reavaliacoes/paciente/{pacienteId}` → `ReavaliacaoResponseDTO[]`
- `GET /reavaliacoes/{id}` → `ReavaliacaoResponseDTO`
- `POST /reavaliacoes` (body: `ReavaliacaoRequestDTO`) → `ReavaliacaoResponseDTO`
- `PUT /reavaliacoes/{id}` (body: `ReavaliacaoUpdateDTO`) → `ReavaliacaoResponseDTO`
- `GET /profissionais?page=0&size=10&sort=nome` → `Page<ProfissionalResponseDTO>`
- `GET /profissionais?page=0&size=10&sort=nome&nome=&email=&tipoContrato=&percentualPagamentoAula=&ativo=true` → `Page<ProfissionalResponseDTO>`
- `GET /profissionais/{id}` → `ProfissionalResponseDTO`
- `POST /profissionais` (body: `ProfissionalRequestDTO`) → `ProfissionalResponseDTO`
- `PUT /profissionais/{id}` (body: `ProfissionalUpdateDTO`) → `ProfissionalResponseDTO`
- `PATCH /profissionais/{id}/ativar` → `204 No Content`
- `PATCH /profissionais/{id}/inativar` → `204 No Content`
- `GET /profissionais/{id}/relatorio-pagamento?inicio=YYYY-MM-DD&fim=YYYY-MM-DD` → `ProfissionalPagamentoRelatorioDTO`
- `GET /profissionais/{id}/relatorio-pagamento/pdf?inicio=YYYY-MM-DD&fim=YYYY-MM-DD` → `application/pdf` com `Content-Disposition: attachment`
- `GET /profissionais/{id}/relatorio-pagamento/xlsx?inicio=YYYY-MM-DD&fim=YYYY-MM-DD` → `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` com `Content-Disposition: attachment`
- `GET /api/nfse-emitidas/paciente/{pacienteId}` → `NotaFiscalEmitidaResponseDTO[]` (frontend chama `/api/api/nfse-emitidas/paciente/{pacienteId}`)
- `POST /api/nfse-emitidas` (body: `NotaFiscalEmitidaRequestDTO`) → `NotaFiscalEmitidaResponseDTO` (frontend chama `/api/api/nfse-emitidas`)
- `GET /api/relatorios/nfse?competencia=MM/AAAA` → `RelatorioNfseResponseDTO[]`
- `GET /api/relatorios/nfse?competencia=MM/AAAA&notaAnteriorEmitida=false` → `RelatorioNfseResponseDTO[]`
- `GET /api/relatorios/nfse?competencia=MM/AAAA&formato=CSV` → `text/csv` com `Content-Disposition: attachment`
- `GET /api/relatorios/nfse?competencia=MM/AAAA&formato=XLSX` → `application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` com `Content-Disposition: attachment`
- `GET /dashboard/resumo` → `DashboardResumoDTO`
- `PUT /api/users/me/senha` (body: `AlterarSenhaRequestDTO` com `senhaAtual`, `novaSenha`, `confirmacaoNovaSenha`) → `204 No Content`

Erros são tratados no subscribe via callback de erro, exibindo mensagem genérica ao usuário.

Rotas com parâmetros numéricos, como `id`, `pacienteId` e `pagamentoId`, usam validação explícita antes de acionar serviços. Apenas inteiros positivos seguros são aceitos. Quando o parâmetro está ausente ou em formato inválido, a tela exibe **Identificador inválido.** e interrompe o carregamento para não gerar URLs de API contendo `NaN`.

## Ferramental de Desenvolvimento

### CodeGraph

O repositório é indexado pelo [CodeGraph](https://github.com/colbymchenry/codegraph), que constrói um grafo semântico do código (símbolos, chamadas, dependências e *blast radius*) consumido por agentes de IA via MCP. O objetivo é reduzir a exploração arquivo por arquivo em um projeto que já passa de 150 arquivos TypeScript, entregando em uma consulta os símbolos relevantes, o código-fonte e quem depende deles.

Decisões de configuração:

- **Servidor MCP versionado no repositório** (`.mcp.json`), e não em `~/.claude.json`, para que a configuração acompanhe o projeto e valha para toda a equipe.
- **Execução via `npx` com versão fixada** (`@colbymchenry/codegraph@1.4.1`), evitando exigir instalação global da CLI e mantendo o comportamento reprodutível entre máquinas.
- **Exclusões em `codegraph.json`**: `assets/` (protótipos HTML e auxiliares `.jsx` do Design System — React em um projeto Angular polui o grafo), `docs/documentacao.html`, `nginx/` e `public/`. O `.gitignore` já é respeitado nativamente, então `node_modules`, `dist`, `coverage` e `.angular/cache` não precisam ser listados.
- **Índice em `.codegraph/`**, adicionado ao `.gitignore` — é artefato local, regenerável por `npx @colbymchenry/codegraph init` e sincronizado automaticamente a cada alteração de arquivo.

A ferramenta é de apoio ao desenvolvimento e não tem qualquer efeito sobre o bundle da aplicação, a imagem Docker ou o pipeline de CI.
